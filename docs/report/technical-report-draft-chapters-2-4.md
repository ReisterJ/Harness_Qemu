# 大模型赋能的开源软件缺陷挖掘与修复验证技术报告初稿

> 本文档为技术报告第 2、3、4 章初稿。第 1 章“概述”和第 5 章“结论”暂不包含在本文档中。内容依据当前原型系统、已有设计文档和截至 2026 年 9 月的实验记录整理，后续可根据正式项目名称、任务书指标和最终实验数据进一步调整。

## 2. 软件缺陷自动化挖掘技术研究

### 2.1 研究背景与技术挑战

开源软件通常具有代码规模大、构建方式复杂、输入接口多样和运行环境差异显著等特点。传统软件缺陷挖掘方法一般依赖静态分析、模糊测试、运行时检测或人工审计中的一种或多种技术，但单一方法在复杂开源软件上容易受到以下因素限制：

1. 静态分析可以发现大量潜在缺陷，但难以准确判断外部输入是否能够到达缺陷位点，容易产生较多误报。
2. 模糊测试能够执行大量输入，但对复杂文件格式、协议状态和对象生命周期条件的理解能力有限。
3. 纯自动化输入生成对复杂文件格式、协议状态和对象生命周期条件的理解能力有限，容易在低价值输入空间中反复搜索。
4. 传统自动化流程往往把“分析漏洞”“构造输入”“执行验证”混合在同一个步骤中，导致分析结论、执行证据和最终漏洞判定之间的边界不清晰。
5. 不同开源项目的构建方式和运行形态差异较大。普通命令行程序、库、网络服务、内核和 QEMU 客体不能使用完全相同的构建和验证方法。

本研究的基本思路是发挥大模型在源码阅读、语义理解、状态推理和输入构造方面的能力，同时使用容器化执行环境、Sanitizer 和运行时观测提供可重复的运行证据。大模型负责提出和修正假设，执行工具负责提供客观观测，独立的 Grade 阶段负责最终确认 PoC 是否有效。

### 2.2 面向源码的静态缺陷分析

#### 2.2.1 静态分析阶段的职责

原始工作流中的 `find` 阶段同时承担源码分析和 PoC 生成任务。当前原型将其拆分为“静态分析”和“动态验证”两个子阶段。静态分析阶段只负责阅读源码、构建配置和项目文档，提出可供动态验证的漏洞候选，不直接生成最终 PoC，也不把静态候选直接当作已确认漏洞。

静态分析 agent 重点完成以下工作：

- 识别外部入口，包括文件、命令行参数、网络请求、协议消息、脚本输入和设备接口等；
- 定位潜在的危险操作，如越界访问、整数溢出、释放后使用、类型混淆、资源生命周期错误和逻辑状态错误；
- 分析攻击者可控数据如何流向候选位点；
- 检查编译选项、功能开关、权限和初始化条件；
- 对调用链、数据流和反例进行审查，排除死代码、测试代码和不可用配置；
- 为动态验证提供输入入口、触发条件、预期观测结果和必要的控制变量。

静态阶段的输出采用结构化 `StaticFinding` 形式，核心字段包括候选编号、漏洞类型、源码位置、外部入口、攻击者可控数据、静态调用链、可达性证据、根因描述、所需条件、动态验证计划和置信度。这样的设计使静态分析结论可以被动态 agent 消费，也便于保存、恢复和审计。

#### 2.2.2 静态结论与动态证据的边界

静态报告中的调用链和触发条件是待验证假设，而不是最终证据。动态 agent 需要重新阅读相关源码，并通过实际运行确认：

- 输入是否能够从真实外部入口进入目标代码；
- 目标函数、基本块或源代码位置是否确实被执行；
- 目标执行是否满足缺陷所需的状态条件；
- 产生的 Sanitizer 事件或逻辑异常是否与候选根因相匹配；
- 结果是否可以在干净目标环境中稳定重放。

因此，静态分析用于缩小搜索范围，动态验证用于判断候选是否具有可执行性，Grade 才是最终 PoC 是否成立的判定环节。

### 2.3 迭代式动态验证与漏洞判定

动态验证采用“假设—执行—反馈—修正”的循环。每一轮至少包含以下步骤：

1. 动态 agent 复核静态候选、源码和入口；
2. 提出本轮输入结构、状态条件和观测目标；
3. 通过统一执行协议运行输入；
4. 收集普通目标程序、Sanitizer 和运行时观测结果；
5. 区分不可达、到达但未触发、走错路径、环境失败和候选已就绪等状态；
6. 根据结果调整输入构造策略，而不是无条件重复相同命令。

动态阶段同时覆盖内存漏洞和逻辑漏洞，但二者使用不同的最终 oracle：

```text
内存漏洞：外部入口 → 候选位点 → 匹配的 Sanitizer 事件 → 稳定复现
逻辑漏洞：外部入口 → 候选位点 → 非法状态 → 错误外部效果 → 稳定复现
```

对于内存漏洞，ASan、UBSan、MSan、KASAN 等工具可以提供较强的运行时证据，但仍需判断崩溃是否发生在候选路径上，避免把无关崩溃、OOM、超时或环境故障误判为目标漏洞。

对于逻辑漏洞，不能简单依赖退出码或 ASan 输出。原型将逻辑验证拆为 `site_reached`、`bad_state_observed`、`bad_effect_observed` 和可重复控制条件等层次。例如，一个整数截断问题不仅需要证明相关代码执行，还需要证明截断后的值导致了后续非法分支或错误输出。

### 2.4 大模型与动态执行反馈融合

大模型在动态验证阶段承担源码理解、状态推理和输入构造职责，Harness 则负责将每次输入转换为可重复、可审计的执行任务。模型先提出输入假设，系统立即运行目标程序并返回退出状态、标准输出、标准错误、Sanitizer 信息、超时和资源状态；模型结合源码和执行结果调整下一轮输入。

这种设计把动态验证从一次性“生成 PoC”转化为多轮假设验证过程。每一轮都保存输入、执行命令、环境、输出和模型判断，既可以支持长时间运行，也可以在失败后恢复。对于复杂的文件格式、协议状态和对象生命周期问题，模型需要逐步构造前置状态，而不是只改变输入长度或随机字节。

需要特别区分模型解释和执行事实：模型可以解释为什么某个输入可能接近漏洞条件，但只有目标程序实际输出的 Sanitizer 事件、逻辑错误或可重复行为才能作为验证证据。无法启动、超时、依赖缺失和资源耗尽也必须独立记录，不能直接标记为误报。

### 2.5 面向多类型目标的构建与运行适配

为了支持不同语言和运行形态，原型增加了从仓库到可运行目标镜像的构建流程。该流程首先由分类 agent 阅读 README、构建脚本、CI 配置和包管理文件，判断项目的语言、构建系统、运行形态、输入入口、检测器和资源需求；随后由构建 agent 生成 Dockerfile、目标 manifest、config、运行契约和必要的辅助文件。

宿主机负责锁定仓库 commit、执行 Docker build、保存构建日志和运行验收。agent 容器不直接控制宿主机 Docker daemon。对普通进程、网络服务、QEMU 和定制目标，系统通过 `process`、`service`、`qemu` 和 `custom` runtime adapter 统一提供启动、就绪检查、执行、重置、日志收集和 PoC 重放接口。用户还可以提供 Docker build/run 参数文件，以支持网络、设备、QEMU 或其他硬件相关配置。

该设计使语言和目标类型成为构建阶段的适配问题，而不是要求在 find、dynamic validation 和 grade 中为每一种语言重复修改主流程。

### 2.6 阶段性成果与不足

当前已经形成以下阶段性成果：

- 完成静态分析与动态验证的阶段拆分，并保持 Grade 作为最终 PoC 验收边界；
- 支持结构化静态报告、动态迭代记录、Sanitizer 证据和逻辑漏洞证据；
- 建立目标镜像、运行契约和用户 Docker 参数的可扩展接口；
- 在 canary、C/C++ 开源项目、MRuby、Ghostscript 等目标上进行了功能和端到端试验；
- 形成了 MRuby 环境写屏障 UAF 等具有源码、触发条件和 Sanitizer 证据的实验案例。

当前仍存在以下限制：大模型输出具有随机性；结构化 PoC 的协议合法性仍会影响正式验收；运行时检测结果可能受到目标构建选项影响；构建工具链、运行时依赖和目标容器可能造成实验污染；不同项目之间的输入接口和验证标准仍需要进一步抽象。

## 3. 软件缺陷自动化修复技术研究

### 3.1 研究目标

缺陷发现之后，如何生成能够真正修复根因、通过编译和测试、且不被相似输入绕过的补丁，是自动化缺陷挖掘系统的重要组成部分。本研究将自动修复定义为“候选补丁生成 + 独立可执行验证”，而不是只生成一段看起来合理的代码差异。

修复阶段的主要目标包括：

- 根据已验证 PoC、Sanitizer 栈、源码和根因分析生成最小补丁；
- 避免只针对单个 PoC 值增加特判，优先修复错误的边界、状态或生命周期不变量；
- 确认补丁能够编译，并使原始 PoC 不再触发；
- 尽可能运行项目已有测试，检查回归；
- 通过新的攻击尝试检查补丁是否只是阻断了单一路径；
- 为人工审查提供补丁、证据、失败日志和验证结果。

### 3.2 自动化修复工作流

当前原型中的 patch 流程以 Grade 已确认的漏洞为输入，整体过程如下：

```text
已验证漏洞与 PoC
        ↓
patch agent 分析根因并生成 diff
        ↓
独立 patch grader 应用 diff
        ↓
编译验证 → 原始 PoC 复现验证 → 回归测试 → 重新攻击
        ↓
通过 / 失败证据
        ↓
失败时将证据反馈给下一轮 patch agent
```

补丁 agent 可以读取源码、PoC、复现命令、Sanitizer 报告和漏洞分析，但其推理过程不会直接成为验收依据。grader 在新的容器中只接收补丁 diff，独立应用并执行验证，从而降低“补丁 agent 自己说补丁有效”带来的偏差。

### 3.3 分层可执行验证机制

原型将补丁验证设计为分层验证梯度：

| 层级 | 验证问题 | 判定方式 |
| --- | --- | --- |
| T0 构建 | 补丁后的源码能否编译 | 应用 diff 后执行目标 `build_command`，检查退出码 |
| T1 原始 PoC | 原始缺陷是否被修复 | 执行 PoC，要求不再产生目标 Sanitizer 或崩溃 |
| T2 回归 | 是否破坏既有功能 | 执行项目 `test_command`；没有测试命令时明确标记跳过 |
| T3 重新攻击 | 是否只是阻断了一个输入 | 从补丁后的镜像启动新的 find agent，检查是否可构造相同根因的变体 |
| T4 风格审查 | 是否符合维护要求 | 由模型进行辅助审查，仅作为建议，不作为硬性通过条件 |

其中，T0—T3 都以可执行结果为主，不能仅凭模型判断通过。尤其是 T3 重新攻击，用于识别“在崩溃点加一个窄条件”这类表面修复。补丁只有在构建、原始 PoC、回归测试（若配置）和重新攻击均通过时，才被标记为完整验证通过。

### 3.4 面向根因的补丁生成策略

修复 agent 的提示和输入材料强调以下原则：

1. 优先修复根因对应的不变量，而不是对 PoC 中的特定长度、字节或路径增加特判；
2. 检查同一危险模式在相邻函数和兄弟调用点是否重复存在；
3. 保持 diff 尽可能小，避免把无关重构混入安全补丁；
4. 在能够加入项目测试的位置增加回归测试；
5. 当修复涉及多个模块、无法确定语义或可能引入较大行为变化时，输出待人工确认的修复方案，而不是伪装成确定补丁。

以 MRuby 环境写屏障漏洞为例，正确的修复方向不是禁止某个具体 Ruby 输入，而是保证环境对象在更新堆上捕获变量后能够被 GC 正确重新扫描。此类漏洞的修复需要理解对象颜色、分代 GC、闭包环境和写屏障之间的关系，因此大模型源码推理与可执行回归验证必须结合使用。

### 3.5 修复研究的阶段性成果

目前已经实现和验证了以下修复基础设施：

- 从已确认漏洞结果目录中读取 PoC、复现命令和 Sanitizer 证据；
- 由独立 patch agent 生成候选 diff；
- 由新的 patch grader 容器执行应用、构建和复现检查；
- 保存每轮 patch 和 re-attack transcript、patch diff、patch result 和失败证据；
- 支持多轮“修复—验证—根据失败原因继续修复”；
- 支持目标提供自定义 re-attack harness，以适配服务、多进程、QEMU 或非文件输入目标。

对于只有静态报告而没有 PoC 的情况，系统也支持静态模式下的补丁草案生成，但该模式不能提供动态漏洞修复证明，结果必须明确标记为静态审查结果。若要证明静态缺陷真实存在，应先构造一个失败测试，再验证修复后测试通过。

### 3.6 现阶段局限与后续方向

当前自动修复仍然不能替代项目维护者审查。主要风险包括：补丁只修复一个触发样例、改变正常语义、引入新的边界错误、遗漏同类调用点，以及项目测试覆盖不足。后续工作包括：

- 自动生成并固化针对漏洞的回归测试；
- 引入差分测试、变异 PoC 和更强的重新攻击策略；
- 对补丁进行静态安全审查和变更范围检查；
- 对同一根因的多个调用点进行模式化修复；
- 将修复结果与上游 commit、项目测试和人工审查流程衔接；
- 为逻辑漏洞增加与缺陷语义对应的可执行 oracle，而不是只依赖进程退出码。

## 4. 大模型赋能的开源软件缺陷模糊测试与修复验证原型系统实现与验证

### 4.1 系统总体架构

当前原型系统围绕“目标构建—缺陷挖掘—独立验证—报告—修复验证”构建，整体流程如下：

```text
开源仓库
   ↓
仓库分类与构建方案生成
   ↓
宿主机 Docker 构建及运行契约验收
   ↓
Recon（可选的攻击面划分）
   ↓
Static Analysis（静态候选生成）
   ↓
Dynamic Validation（输入构造和迭代验证）
   ↓
Grade（干净容器中的最终 PoC 验收）
   ↓
Judge / Report（去重、严重性和可利用性分析）
   ↓
Patch / Re-attack（候选修复及回归验证）
```

系统的核心设计原则是分离不同角色的权限和证据边界：静态分析 agent 不能把文字结论直接升级为漏洞；动态 agent 不能绕过统一执行协议伪造执行结果；Grade 在独立环境中只信任可重放的 PoC；修复 grader 不信任 patch agent 的自我判断。

### 4.2 目标构建与运行环境

系统为每个目标维护 Dockerfile、config、target manifest、构建计划和运行契约。构建流程主要包括：

1. 锁定仓库分支对应的最新 commit，或使用用户明确指定的 tag/commit；
2. 将源码快照作为 Docker build context，避免 Dockerfile 在构建时不受控地拉取其他版本源码；
3. 由构建 agent 依据项目文档生成 Dockerfile、编译命令、入口程序和验收脚本；
4. 由宿主机执行 Docker build，保存完整日志；
5. 通过运行契约检查程序、服务或 QEMU 是否能够启动、就绪、执行最小操作并重置；
6. 只有构建和运行验收都通过后，才将目标镜像发布给后续 find、grade 和 patch 阶段。

目标 manifest 将语言、运行形态、检测器、资源、输入方式和工作流阶段解耦。当前 runtime adapter 包括普通进程、网络服务、QEMU 和 custom 扩展；用户提供的 Docker 参数文件可以为目标补充设备、网络、端口、特权能力和 QEMU 所需配置。

### 4.3 缺陷挖掘阶段的组件实现

#### 4.3.1 Static Analysis

`harness/static_analysis.py` 和静态分析提示负责启动只读分析 agent，读取目标源码和静态报告输入，生成 `static_analysis.json` 与对应 transcript。静态结果包括候选列表、排序、源码证据、入口和动态验证计划。

#### 4.3.2 Dynamic Validation

`harness/dynamic_validation.py` 负责创建动态验证容器、加载候选、运行 agent、保存每轮记录和生成最终 `dynamic_validation.json`。动态 agent 可在同一会话中反复阅读源码、产生输入、观察目标输出并修改假设。

内部采用统一执行协议，输入先写入请求专属目录，Harness 负责普通目标执行、环境重置、输出截断、超时控制和结果关联。动态阶段支持 `candidate_ready`、`false_positive`、`environment_blocked` 和 `iteration_exhausted` 等状态，避免将环境问题错误标记为误报。

#### 4.3.3 运行时观测与统一执行协议

统一执行协议负责接收 agent 生成的输入，并在受控的目标环境中执行。输入在提交时复制为不可变快照，系统记录唯一请求标识、输入摘要、程序参数、退出码、标准输出、标准错误、Sanitizer 结果、超时和资源状态。对于服务和 QEMU 目标，协议还提供启动、就绪检查、执行、重置和日志收集操作。

运行时观测结果与模型解释分开保存。系统将结果区分为正常退出、目标崩溃、Sanitizer 事件、逻辑异常、超时、资源耗尽、启动失败和未知状态，避免把环境故障误当作漏洞结果。必要时可以使用通用插桩或日志观测辅助定位，但这些观测材料不能替代最终 PoC 和 Grade。

#### 4.3.4 Grade、Judge 和 Report

Grade 在新的目标容器中重新执行动态阶段交付的 PoC，只将 PoC 字节和必要的运行参数跨越阶段边界。内存漏洞要求出现匹配的崩溃或 Sanitizer 事件；逻辑漏洞要求出现可重复、输入可控的非法语义状态或错误外部效果。

通过 Grade 的结果再进入 Judge，判断是否为新缺陷、已有缺陷的更好复现或重复结果。Report agent 根据 PoC、源码和运行证据生成可利用性分析，最后由报告 grader 检查报告中的源码位置、运行现象和严重性判断是否有证据支撑。

### 4.4 结果目录与可追溯性

每次实验持久化保存以下材料：

```text
results/<target>/<timestamp>/
  static_analysis.json
  static_transcript.jsonl
  dynamic_validation.json
  dynamic_transcript.jsonl
  iterations/round-*.json
  symbolic_execution/
    request.json
    summary.json
    replay-round-*.json
  poc.*
  grade_transcript.jsonl
  result.json
  reports/bug_*/
```

这些文件分别承担候选分析、动态过程、运行时观测、PoC、最终 Grade 和报告审计职责。实验汇总中还记录动态耗时、agent 工具调用、模型消息、token 分类和最终状态，用于区分模型行为、环境故障与输入搜索策略的影响。

### 4.5 原型系统验证

#### 4.5.1 功能验证

原型已经在 canary 和多个开源目标上进行了端到端验证，覆盖普通 C/C++ 程序、库型目标、结构化输入以及需要复杂运行状态的目标。验证内容包括：

- 目标镜像构建、入口程序和运行契约验收；
- 静态候选生成及结果持久化；
- 普通目标输入执行、超时和输出截断；
- 动态验证迭代状态记录；
- Grade 在干净容器中的重复验证；
- 失败任务、无效 PoC、环境阻塞和超时的分类。

实验过程中发现，PoC 接口合法性、辅助进程超时、Sanitizer 自身崩溃、目标构建差异和模型上下文长度都会显著影响端到端结果。因此，系统将“技术上观察到崩溃”“动态阶段提交成功”“Grade 正式通过”分开记录，而不把它们合并成一个布尔值。

#### 4.5.2 MRuby 案例验证

MRuby 环境写屏障 UAF 是当前较完整的动态验证案例。测试目标为 `n132/arvo:57672-vul`，目标漏洞位于 `mrb_env_unshare` 相关的闭包环境与分代 GC 交互路径。实验输入需要构造闭包、推动环境晋升、写入年轻对象、触发环境脱离栈和后续 GC，最终通过闭包访问失效对象。

该案例表明，复杂漏洞的动态验证不能只依赖随机改变输入长度，而需要将源码中的对象生命周期和 GC 状态转换落实到可执行的输入序列中。实验中通过 ASan 检测到稳定的 heap-use-after-free，并在干净目标环境中重复执行确认了触发条件。该案例在本报告中只用于说明大模型源码分析与运行时验证的结合，不用于评价仍处于验证阶段的其他辅助技术。

#### 4.5.3 结果评价指标

当前原型采用以下指标评价系统：

1. 规定时间预算内是否生成有效 PoC；
2. PoC 是否在干净目标上稳定重放，并通过 Grade；
3. 从动态阶段开始到首次稳定 PoC 的时间；
4. 不同目标类型的成功率、超时率、错误类型和平均耗时；
5. 动态验证过程中输入结构和搜索策略是否发生可解释变化；
6. 目标程序执行时间、工具调用、token 和上下文长度对结果的影响；
7. PoC 在干净环境中的重复成功率和最小化程度。

在正式对比实验中，应固定目标版本、静态报告、模型、时间预算、turn/output 限制和 PoC 接口，并进行多组重复。实验结果应分开报告“技术上发现候选”“提交协议接受”和“Grade 通过”三种状态。

### 4.6 系统当前问题与改进方向

当前原型已经能够支撑完整的研究闭环，但仍需重点改进以下方面：

- 统一不同目标类型的 PoC 描述和执行协议，降低模型提交无效结果的概率；
- 对轨迹截断、异常退出、PIE/ASLR、Sanitizer 自身崩溃和工具链不兼容进行更明确的错误隔离；
- 优化结构化输入的种子保存、语法保持变异和多轮执行结果关联；
- 通过更严格的时间预算、token 统计和重复实验，分离输入搜索策略、运行环境和模型随机波动；
- 将逻辑漏洞的非法状态和错误外部效果进一步标准化，使 Grade 能够覆盖不产生崩溃的缺陷；
- 将补丁生成、回归测试和重新攻击纳入统一的实验报告指标。

总体而言，当前系统已经从单一的“LLM 生成 PoC”原型扩展为具有目标构建、静态分析、动态验证、独立 Grade 和自动修复验证能力的模块化原型。其阶段性结果表明，大模型源码分析与可执行验证之间存在明显的互补空间，但跨项目的稳定性仍需要通过更严格、更多重复的对比实验进一步验证。
